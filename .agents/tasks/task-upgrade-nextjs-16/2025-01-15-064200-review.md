# Next.js 16 upgrade with Turbopack and async params migration

The application moves from Next.js 15.5.4 to 16.2.6, bringing React 19.2.6, the Turbopack default, and the async route params breaking change. The upgrade renames `middleware.ts` to `proxy.ts` (with the exported function rename), removes the now-unnecessary webpack config, and updates `createApiHandler` to await the newly-promisified `params` object. Tests and type declarations were updated to match.

**Watch for:** the proxy file rename may not be picked up correctly by Next.js 16's runtime — the `config` export with a matcher still follows the old middleware convention and needs verification that it actually runs (confirmed). The version pinning strategy switched from exact to caret ranges for `next`, `react`, and `react-dom`, which silently allows minor/patch drift between environments (confirmed).

## High-level view

The most significant behavioral change is in `lib/middleware/api.ts` where the route context `params` goes from a synchronous record to a `Promise<Record<string, string>>`. The fix awaits it once at the top of the handler wrapper and passes the resolved value downstream, avoiding double-await bugs in individual route handlers.

The `middleware.ts` → `proxy.ts` rename follows Next.js 16's documented breaking change, but the file still exports a `config` object with `matcher` — this pattern was middleware-specific and may not be recognized by the proxy convention. If it's ignored, CORS enforcement and request size checking silently stop running.

The webpack `ignoreWarnings` for the Sentry dynamic import was removed along with the rest of the webpack config. Turbopack has no equivalent suppression mechanism, so the warning may now appear in build output.

Version ranges for `next`, `react`, and `react-dom` moved from pinned to caret (`^`), allowing patch drift across environments unless the lockfile is always present.

## Proxy rename and route matching

The file was renamed from `middleware.ts` to `proxy.ts` and the exported function from `middleware` to `proxy`. The body is unchanged — CORS handling, request size checking, security header injection. The `config` export remains:

```typescript
export const config = {
  matcher: ["/api/:path*"],
}
```

In Next.js 15, this `config.matcher` told the framework which paths to run the middleware on. The Next.js 16 migration guide renames the concept, but whether `proxy.ts` still respects a `config` export with `matcher` is ambiguous. If it doesn't, this file will never execute and all API requests will skip CORS enforcement and size checking. This is the highest-priority item to verify manually — hit an API route and confirm the `X-Request-ID` header (set by the proxy) appears in the response.

## Async params in createApiHandler

The route context signature changed from `{ params?: Record<string, string> }` to `{ params?: Promise<Record<string, string>> }`. The implementation resolves it once at the top:

```typescript
const resolvedParams = context?.params ? await context.params : undefined
```

This is passed to both `apiContext.params` and `validateRequestData`. Individual route handlers (`app/api/npcs/[id]/route.ts`, etc.) continue reading `ctx.params?.["id"]` unchanged — the await happens in the wrapper, keeping route code clean.

## Version pinning change

Before this PR, `next`, `react`, and `react-dom` were pinned to exact versions (`"15.5.4"`, `"19.1.0"`, `"19.1.0"`). They now use caret ranges (`"^16.2.6"`, `"^19.2.6"`). The lockfile pins exact resolved versions, so builds from the committed lockfile are reproducible. But any `bun install` without a lockfile (or after a lockfile deletion) will resolve the latest compatible version, potentially introducing untested changes.

## Webpack removal and Sentry warning

The webpack config block suppressed a "Critical dependency" warning from the optional Sentry integration's dynamic import. With Turbopack as the default bundler in Next.js 16, webpack config is ignored anyway. The Sentry code uses a runtime `import()` wrapped in try/catch, so it won't break the build — but the warning may now appear in Turbopack's output since there's no equivalent `ignoreWarnings` mechanism.
