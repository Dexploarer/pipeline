# Security audit remediation — fixes verified, auth propagation gap introduced (v2)

The four critical issues from the v1 review have been addressed: v1 agent routes now have auth guards, workflow sub-routes (`/ai-generate`, `/voice-config`, `/export`) require authentication, the in-memory rate-limit map prunes expired entries on every 100th call or when size exceeds 1000, and the health endpoint returns 503 when degraded. The remaining three low-priority items (hardcoded `equals`, CORS production origin, session cleanup O(n)) are acknowledged as acceptable.

Watch for: The `WorkflowExecutor` now fetches sub-routes that require auth, but its internal `fetch` calls include no `Authorization` header — these calls will receive 401 in production (confirmed). Two workflow routes (`/api/workflow/failure`, `/api/workflow/store`) are still unprotected but were not touched in this diff and are out of scope.

## High-level view

Adding auth guards to the workflow sub-routes created a self-inflicted compatibility break. The `WorkflowExecutor` in `lib/workflow/executor.ts` calls `/api/workflow/ai-generate`, `/voice-config`, and `/export` via server-side `fetch` with only a `Content-Type` header. Since those routes now reject requests without a valid `Authorization` header, any workflow execution triggered through `/api/workflow/execute` will fail at the first AI generation, voice, or export node. The executor needs to either receive and forward the caller's token or use a service-level credential for internal calls.

The rate-limit pruning uses the current call's `windowMs` to decide which entries are expired. Since the in-memory store is shared across all rate-limit configs, a call with a short window (e.g., `API_STRICT` at 60s) will prune entries created under a longer window (e.g., `AI_GENERATION` at 3600s) prematurely. The practical impact is that a caller could get extra requests allowed after the premature prune resets their counter. The size cap at 1000 entries prevents unbounded growth regardless.

## Executor-to-sub-route auth propagation gap

The `/api/workflow/execute` route validates the caller's auth header:

```typescript
const authHeader = req.headers.get("authorization")
const user = await getUserFromRequest(authHeader)
if (!user) {
  return NextResponse.json({ error: "Authentication required" }, { status: 401 })
}
```

It then instantiates `WorkflowExecutor` and calls `executor.execute(nodes, edges, input)`. The executor's `executeAIGenerationNode` (and voice/export equivalents) builds a fetch request:

```typescript
const response = await fetch(`${getApiBaseUrl()}/api/workflow/ai-generate`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ ... }),
})
```

No `Authorization` header is included. Since the v2 fix added auth guards to all three sub-routes, this fetch will return 401, the executor will see `!response.ok`, throw `"AI generation failed: Unauthorized"`, and the workflow execution will fail.

The fix is to thread the caller's auth header into the executor — either by passing it to the `execute()` method and storing it in `WorkflowContext`, or by having the executor attach a service-level secret that the sub-routes accept as an alternative to user auth. The former is simpler and maintains the audit trail (the sub-routes see the original user identity).

## Rate-limit pruning with mixed windows

The pruning loop uses the current call's `windowMs` to decide which entries are expired:

```typescript
for (const [entryKey, entry] of inMemoryStore) {
  if (now - entry.windowStart > windowMs) {
    inMemoryStore.delete(entryKey)
  }
}
```

If route A uses `AI_GENERATION` (window: 3600s) and route B uses `API_STRICT` (window: 60s), a pruning pass from route B (windowMs = 60000) will delete entries older than 60 seconds — including entries from route A that are still within their valid 3600-second window. This means an AI_GENERATION entry could be pruned prematurely, resetting that caller's rate-limit counter and allowing extra requests.

Storing the original `windowMs` alongside each entry and comparing `now - entry.windowStart > entry.windowMs` during pruning would make the check correct across mixed configurations.
