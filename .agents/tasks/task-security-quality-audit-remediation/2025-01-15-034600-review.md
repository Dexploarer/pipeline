# Security and quality audit remediation across 29 findings

This change hardens a Next.js AI game-development platform against a 29-item audit. The work spans authentication enforcement on 7 previously-open API routes, session store hardening with TTL/LRU eviction, CORS tightening (origin echo instead of wildcard), in-memory rate-limit fallback, audit-log DB persistence, conditional workflow node evaluation, CSP expansion, lazy env validation, structured logging, Redis pipeline for mset, deprecation headers on v1 agent routes, and a health-check endpoint with CI workflow.

Watch for: V1 agent routes (`/api/agents/*`) still have no auth checks — only deprecation headers (confirmed). The `equals` operator in conditional node evaluation hardcodes comparison to `true`/`"true"` rather than accepting a user-supplied comparand (confirmed). The in-memory rate-limit fallback map grows without bound across the process lifetime (confirmed). The health endpoint always returns HTTP 200 even when degraded (likely intentional but worth noting for monitoring consumers).

## High-level view

Authentication is added to v2 agent endpoints and the generation/workflow routes via `getUserFromRequest`, which in development mode accepts any Bearer token when `VERCEL_ENV` is unset or `"development"`. The v1 agent routes remain unauthenticated; they gain only `X-Deprecated` headers. This means an attacker can still hit the v1 session/action/stream endpoints without credentials in production until they are removed.

The new `SessionStore` replaces raw `globalThis` maps for v2 sessions, enforcing a 100-session cap and 30-minute TTL with LRU eviction. The v1 routes still use an unbounded `globalThis.agentSessions` map, but since those are deprecated and presumably short-lived, the asymmetry is acceptable as a transitional state.

CORS now echoes the request's `Origin` only when it matches an allowlist (`localhost`, `*.vusercontent.net`, `*.v0.app`). The old code set `Access-Control-Allow-Origin: *` for any request whose destination hostname matched those patterns — a fundamentally different (and less useful) check.

The workflow executor resolves internal fetch URLs through a `getApiBaseUrl()` helper (checking `NEXT_PUBLIC_API_URL`, then `VERCEL_URL`, then localhost). Conditional nodes now evaluate against `context.results` with operators `exists`, `not_empty`, `equals`, `greater_than`, and a truthiness default. The `equals` operator's semantics are surprisingly narrow.

Rate limiting gains an in-memory `Map`-based sliding window when Redis is unavailable. The map is never pruned of stale entries for identifiers that stop making requests. For short-lived serverless invocations this is a non-issue, but for long-running Node processes it constitutes a slow memory leak.

Environment validation moves from eager (import-time crash) to lazy (`getEnv()` on first call), gated by `SKIP_ENV_VALIDATION` in CI and build contexts. The `next.config.ts` uses a top-level `await import()` which requires ESM module resolution — this works in Next.js 15 but is worth noting for anyone backporting.

## V1 agent routes: deprecated but still open

The four v1 routes under `/api/agents/` gain `X-Deprecated: true` response headers and a deprecation comment at the top of each file, but no authentication check. These routes still use a raw `globalThis.agentSessions` map without TTL or size limits. Since the v2 routes now require auth, the v1 routes become the path of least resistance for an unauthenticated caller. The session/stream endpoints spin up LLM inference (Anthropic calls), so an attacker can run up costs.

The mitigation is either to add the same auth check here or to remove the routes entirely since the deprecation is in place.

## Conditional node `equals` operator hardcoded to boolean true

```typescript
case 'equals':
  conditionMet = evaluatedValue === true || evaluatedValue === 'true'
  break
```

The name "equals" implies comparison between two values, but the implementation only checks for truthiness against literal `true`. There is no way to compare a result value against an arbitrary expected value because `node.data` only destructures `condition` and `operator` — there is no `value` or `comparand` field. This makes the operator name misleading and limits the usefulness of conditional branching in workflows.

## In-memory rate-limit map never pruned

The `inMemoryStore` Map at module scope accumulates entries for every unique `identifier` that hits the rate limiter when Redis is down. Once a window expires, the entry is reset on next access but never deleted if that identifier never returns. In a serverless environment each invocation is short-lived so this is unlikely to matter. In a long-running Node process (e.g. `bun run dev`), the map grows monotonically.

A simple fix: delete the entry when the window resets instead of updating it in-place, or cap the map size.

## Health endpoint status code

```typescript
return NextResponse.json({ status, ... }, { status: 200 })
```

The response body distinguishes `"ok"` from `"degraded"`, but the HTTP status is always 200. Load balancers and monitoring systems that rely on HTTP status codes will not detect a degraded state. Returning 503 when checks fail is the common convention for health endpoints consumed by infrastructure.

## Workflow sub-routes unprotected

The `WorkflowExecutor` calls `/api/workflow/ai-generate`, `/api/workflow/voice-config`, and `/api/workflow/export` via `fetch`. Auth was added to `/api/workflow/execute` (the entry point), but these downstream routes have no auth guard — verified by reading `app/api/workflow/ai-generate/route.ts`. The executor's internal fetches succeed because the downstream routes are open, but this also means anyone can call those routes directly to trigger AI generation, voice configuration, or export without authentication.

Either add auth guards to all workflow sub-routes, or make them internal-only by checking for a shared secret header that the executor includes.

## CORS allowlist completeness

The `isAllowedOrigin` function allows `localhost`, `*.vusercontent.net`, and `*.v0.app`. These are all Vercel preview/development domains. If the application is deployed to a custom production domain (e.g. `app.example.com`), legitimate browser requests from that origin will not receive CORS headers. The function would benefit from reading an additional `ALLOWED_ORIGINS` env var for production domains.
