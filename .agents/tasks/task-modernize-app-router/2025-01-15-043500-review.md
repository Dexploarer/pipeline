# App Router migration with persistent dashboard shell

The monolithic single-page tab-switching architecture in `app/page.tsx` has been replaced with Next.js App Router file-based routing. A `(dashboard)` route group wraps 14 page routes under a shared layout that provides a collapsible sidebar and fixed header. The old page (422 lines of lazy-loaded tab panels) is deleted; each tab becomes its own route. The agents page was simultaneously updated to hit v2 API endpoints, Google Fonts are enabled, a global Toaster is added, and the `next.config.ts` top-level await issue is removed.

**Watch for:** The dashboard layout is entirely client-rendered (`"use client"`) which disables metadata exports and server-side rendering for all child routes (confirmed). The workflow-studio page lives outside the `(dashboard)` group and renders without the sidebar shell (confirmed). Google Fonts re-enabled despite the prior explicit comment about offline build environments (confirmed).

## High-level view

The structural bet is a `(dashboard)` route group that owns navigation chrome. Every route inside inherits a fixed header and a collapsible sidebar, giving the app a persistent shell without re-mounting on navigation. The sidebar state (collapsed/expanded, mobile open) lives in React state inside the layout, which resets on hard refresh but persists across client-side navigations.

Most of the 14 new page files are thin wrappers that lazy-load an existing component with ErrorBoundary + Suspense. The only substantive pages are the dashboard home (health check + quick actions), analytics (real `/api/health` data), settings (static API key display), and agents (v2 API migration). This keeps the routing migration low-risk since the actual component logic is unchanged.

The `next.config.ts` change removes a top-level `await import()` that broke environments where the config loader doesn't support ESM top-level await. Env validation is deferred to runtime, which means misconfigured deployments won't fail at build time but will fail on first request.

## Dashboard layout as a client component

The entire `app/(dashboard)/layout.tsx` is marked `"use client"`. This is necessary for the sidebar collapse state and mobile menu toggle, but it has a cascading effect: every child page is rendered client-side even when no interactivity is needed (e.g., the static settings page, the placeholder pages for lore/dialogue/simulator that just wrap a lazy component).

The standard pattern in App Router is to keep the layout as a server component and push client interactivity into child components. The sidebar itself (`DashboardSidebar`) is already a separate client component — the layout could import it as a client island rather than being client-rendered entirely. The mobile overlay and collapse toggle could live in a `<DashboardShell>` client component that wraps `{children}`, while the layout stays server-rendered.

Consequence: `export const metadata` won't work in any `(dashboard)` page. The root layout still has metadata, so the top-level title/description applies everywhere, but per-page titles (useful for browser tabs) aren't available without `useEffect` + `document.title` or restructuring.

## Workflow studio isolation

`app/workflow-studio/page.tsx` sits outside the `(dashboard)` group and therefore doesn't inherit the sidebar/header layout. Its "Back to Workflows" link points to `/workflows` (which is inside the dashboard). Navigating back and forth creates a jarring UX shift — the sidebar appears/disappears.

The page uses `container mx-auto` for its own layout, whereas dashboard pages rely on the layout's `max-w-7xl mx-auto` wrapper. This suggests the page should either be brought into the dashboard shell or given its own minimal header to avoid the visual discontinuity.

## Active link detection edge case

The sidebar uses `pathname.startsWith(item.href)` for active state. Since `/` is handled specially (`pathname === "/"`), this works for the current route set. However, `/world` would also match a future `/world-builder` route. Low risk given there are no such routes today, but worth noting for future route additions.

## Google Fonts re-enabled

The diff un-comments the `Geist` and `Geist_Mono` font imports from `next/font/google`. The prior version explicitly noted these were disabled "for build environments without network access." Re-enabling them means builds in network-isolated CI will fail at the font download step. If CI is the concern, `next/font/local` with vendored font files would eliminate this dependency entirely.

## Build-time env validation removed

The previous code:

```ts
if (!process.env["SKIP_ENV_VALIDATION"]) {
  const { getEnv } = await import("./lib/config/env")
  getEnv()
}
```

This is replaced with a comment explaining env validation happens at runtime. The trade-off: a deploy with missing env vars won't fail the build but will fail on first API request. This removes a fast-fail mechanism for operators who relied on build-time checks.
