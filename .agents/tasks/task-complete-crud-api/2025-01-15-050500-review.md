# Complete CRUD API for game entity types

Fifteen new API route files implement RESTful CRUD for seven entity types (NPCs, Quests, Zones, Lore, Relationships, Dialogue Trees, Content Packs) plus a Search endpoint. Each route uses the existing `createApiHandler` middleware for auth, validation, and rate limiting. Mutation endpoints log to audit and invalidate cache. Three test files cover NPC, Zone, and Search routes with 17 tests, mocking the middleware layer to test handler logic in isolation.

**Watch for:** DELETE and PUT handlers proceed with audit logging even when the target entity doesn't exist (confirmed). The search endpoint only supports NPC search and reflects the unsupported `type` parameter directly into the error response (confirmed). In-memory filtering after full-table fetch on multiple list endpoints will degrade at scale (likely).

## High-level view

All 14 entity routes follow an identical template: GET list with pagination and entity-specific filters, POST with schema validation, GET by ID with 404 handling, PUT with validation, DELETE. The uniformity means a single design flaw (like the missing existence check before delete) is replicated across all seven entity types.

The list endpoints for Zones, Content Packs, and Lore fetch all records from the database and filter in-memory using `.filter()`. This works at low record counts but becomes a performance cliff once tables grow, with no safeguard or comment acknowledging the trade-off.

The search endpoint is limited to NPC semantic search; other entity types get a hard error rather than a text-based fallback (the `searchNPCsByText` function exists in the search module but isn't wired up). The endpoint reflects the user-supplied `type` parameter into the error message without sanitization.

The test suite mocks `createApiHandler` itself to avoid the double-body-read problem in jsdom. This means the tests exercise handler logic (repo calls, audit, cache invalidation) but do not test that validation schemas, auth, or rate limiting are actually wired correctly for each route.

<summary>Issues (5)</summary>

1. **DELETE without existence check** — All seven `[id]` route files call `deleteXxx(id)` followed by `createAuditLog("delete", ...)` without verifying the entity exists first. A delete of a non-existent ID produces a bogus audit log entry. Add a GET-then-404 check before the delete, or have the repository return a boolean/count indicating whether a row was actually deleted.
2. **PUT without existence check on repo error** — If `updateXxx(id, body)` throws because the ID doesn't exist (as the repo implementations do), the error propagates as a 500 via `handleError` rather than a 404. Catch the repo's "not found" throw and return `errorResponse(..., 404)`, or check existence first.
3. **Reflected input in search error** — `app/api/search/route.ts` interpolates the raw `type` query parameter into the error message (`Unsupported search type: ${type}`). Sanitize or omit the value to prevent log injection or UI confusion.
4. **Full-table fetch with in-memory filter** — Zones (filter by `type`/`parentZoneId`), Content Packs (filter by `category`/`status`), and Lore (fallback to `getAllLoreEntries`) load the entire table then filter client-side. Add a TODO or pagination-at-DB note if this is accepted tech debt; otherwise implement WHERE-clause filtering.
5. **Test coverage gap on middleware wiring** — Tests mock `createApiHandler` entirely, so they cannot verify that the correct validation schema, auth flag, or rate limit config is actually passed to the middleware for each route. Consider at least one integration-style test per entity type that uses the real `createApiHandler`.

## DELETE and PUT on non-existent entities

Every `[id]/route.ts` DELETE handler calls the repo's delete function and then unconditionally writes an audit log and invalidates cache. The underlying repo executes `DELETE FROM ... WHERE id = $1` which silently succeeds with zero affected rows when the ID doesn't exist. The result: a "delete" audit entry for an entity that was never there, and a 200 response with `"success": true`.

```typescript
// app/api/npcs/[id]/route.ts — DELETE handler
await npcRepo.deleteNPC(id)          // no-op if ID doesn't exist
await createAuditLog("delete", "npc", id)   // logs anyway
await invalidateEntity("npc", id)           // invalidates anyway
return successResponse(null, "NPC deleted successfully")  // reports success
```

This pattern repeats across all seven entity types. The GET handler on the same file already demonstrates the correct existence check — the same check should gate DELETE.

For PUT, the repos throw `Error("Failed to update ...")` when `RETURNING *` returns nothing (no row matched). This throw propagates to `createApiHandler`'s catch block, which returns a 500 with a generic "Internal server error" message. The client never sees a 404, and the error logs imply a server fault rather than a missing resource.

## Reflected user input in search error

```typescript
// app/api/search/route.ts
return errorResponse(
  `Unsupported search type: ${type}`,
  "UNSUPPORTED_TYPE",
  400,
)
```

The `type` parameter is user-controlled and passed directly into the response body and logs. This can be exploited for log pollution (the middleware logs the response) or monitoring confusion with long/malformed values. Use a static message or enumerate allowed values.

## In-memory filtering at scale

The Zones GET route calls `zoneRepo.getAllZones()` then applies `.filter()` for `type` and `parentZoneId`. Content Packs does the same for `category` and `status`. Lore falls through to `getAllLoreEntries()` when no filter params match. In each case the full table is loaded into Node memory before pagination slices it.

The NPC route handles this better by delegating `zoneId` filtering to `getNPCsByZone` at the repository level. No equivalent repository-level filtering exists for zone type, content pack category/status, or the lore "no filter" case.

## API asymmetry: required filters on some list endpoints

`GET /api/dialogue-trees` returns 400 if neither `npcId` nor `questId` is supplied. `GET /api/relationships` returns 400 without `entityId`. Other entity types return all records when no filter is provided. Consumers will need to handle this asymmetry — a generic "list entities" client abstraction won't work uniformly across all seven types.

## Search endpoint scope

The task description specifies "text-based fallback using the respective repo's getAll + filter" for non-NPC types, and `searchNPCsByText` already exists in `lib/search/api.ts`. The endpoint only implements NPC semantic search and returns a hard error for any other `type` value. This is functional but doesn't fulfill the stated multi-type search intent.

## Test coverage gaps

Not covered by the 17 tests: error responses from repo failures (the PUT 500 path that should be a 404), pagination edge cases (page beyond total), the archetype and search filter branches in the NPC list endpoint, and any verification that the correct validation schema or auth config is wired to each route.
